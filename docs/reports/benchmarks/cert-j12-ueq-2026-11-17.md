## `LAT171-1` c379 replay gap

The source parent c41 is `X0 = meet(X0, join(X0, X1))`; the target parent c341
has a right side that, after standardizing its variables apart, matches c41's
right side with `X0 = meet(Y1, Y5)` and `X1 = join(V, W)`, where
`V = meet(Y1, meet(Y2, meet(Y5, join(Y1, Y5))))` and `W = meet(Y2, Y5)`. The
rewrite yields c379 exactly, using associativity of meet and join; target
variables remain rigid, and commutativity is not needed for this step.

The exact AC unifier rejects the unequal flattened operand counts before the
source variable can absorb the `Y1, Y5` meet segment. The AC subset matcher was
then only trying one-to-one operand pairing. The kernel now also tries the
associative contiguous-segment matcher for an AC symbol when the AC subset
search fails. This keeps the original AC search and rigid-target checks while
admitting this valid associative instance. The regression test also checks a
forged conclusion is not certified.

With that change, a newly built local `mrs-proover` (SHA-256
`14ba295d39f887bb87773f0cc06f8de541cd1b098ba3f62451a0532d1419ea1a`) replays
**all 50** previously unresolved proofs as `VerifiedGood` with
`TPTP=/home/hack/TPTP-v9.3.1`. This was a diagnostic replay with a different
TPTP version and did not update the archived audit. The exact v9.0.0 re-audit
below now supersedes the archived 97/50 split for proof certification. The
v9.3.1 local replay can be repeated from the repository root with:

```bash
run=/home/hack/campaign-casc-j12-ueq-W8CASCHJ1-99-20261117
proofs="$run/certification/proofs/mrs-starexec/ueq"
awk -F, 'NR > 1 && $14 == "Unknown" { print $3 }' "$run/certification/audit.csv" |
  while IFS= read -r problem; do
    TPTP=/home/hack/TPTP-v9.3.1 \
      target/release/mrs-proover --strict --problems-dir "$proofs" \
        "$proofs/$problem.s"
  done
```

The exact-version re-audit was completed on 2026-11-19; its identity, digests,
and strict verdict counts are recorded below.

## Comparability and interpretation

This was one sequential campaign (`jobs=1`) with eight search workers and
cross-strategy sharing disabled (`MRS_SHARED_POOL_INTERVAL=0`). The run log
confirms the official **180-second UEQ limit**; `run_meta.json`'s 120-second
`default_time_limit` is not the applied budget because `use_casc_times=1`.

`MRS_HARDWARE=casc` sets eight workers but does not pin them to eight physical
cores. The host, `teenf9901`, had 16 physical cores and 128,019 MB RAM; the
prover reports 108,816 MB effective memory against the 131,072 MB configured
allowance (`mem_unrepresentable=1`). Thus the run did not reproduce the
canonical eight-physical-core, full-memory CASC machine. There is no paired J12
baseline here, so neither the solve count nor family differences establish a
schedule or source effect. Do not compare this result as if it replaced
CASC-J13 or CASC-30 UEQ measurements; it is a separate edition and corpus.

The producer tree was marked dirty at commit `9c10581`. The binary used Rust
1.100.0 and has SHA-256
`729795586743042bee969760347500b953599648180045911f06f5ee42351118`. Treat
147/300 as the raw result of that binary and setup, not an official CASC score
or a fully re-audited score.
