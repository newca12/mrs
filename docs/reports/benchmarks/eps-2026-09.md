# EPS: reaching the SAT tier, and two optimisations that had to be reverted

> Status: current. Branch `feat/eps-casc-sim-exploration`, commits `9132b1e`
> through `37d411c`. Measured on `crates/mrs-bench/problems/casc-30` with
> `MRS_HARDWARE=casc-sim`, `--casc-times` (120 s for EPS), certified track
> alone. Every `Satisfiable` answer reported here is checked by the proof
> kernel's independent model validator.

## Why EPS was at 12/100

EPS asks for `Satisfiable`, and nothing in the ordinary portfolio can produce
one: `given_clause.rs` returns `GaveUp` even for a cleanly saturated clause
set, because the engine is not yet proven complete with respect to indexing,
simplification and cancellation. So EPS coverage came entirely from
`--certify-ordered`, and that path answered 12/100.

Almost none of the other 88 was a search-power problem. The certified path
could not *reach* an answer, and `TRACE_CERTIFY=1` showed the same symptom in
every case: a run that spends its whole budget and reports `GaveUp`.

## The fix that worked: the SAT tier was unreachable

`certify_ground_ordered_resolution` routed with

```rust
if tier1 {
    return run_tier1(..);   // hard return
}
```

`run_tier1` computes a double ordered-resolution closure, which is exponential
in the grounding size. On a grounding that clears the Tier-1 size gate it
cannot close — and when it gave up it returned `Limit`, which propagated
straight out of the router. Tier 2, the CaDiCaL path that decides the *same
ground CNF* propositionally, was unreachable for exactly the inputs it was
written for.

GRP125-2.004, before and after:

| | before | after |
|---|---|---|
| closure growth | 11 603 clauses, 304k inferences in 15 s, no close | not attempted |
| Tier 2 | never reached | 10 ms, model re-verified |
| verdict | `GaveUp` at 107 s | `Satisfiable` at 0.01 s |

Tier 2 now runs first. The encoding is linear in a grounding that is already
materialized, so the call is cheap even on the small groundings the closure can
close, and a satisfiable verdict is re-checked clause by clause against the
problem, so it does not depend on an ordering at all. Tier 1 keeps the whole
remaining budget for the direction only it can perform — a refutation carrying
TSTP ancestry — and Tier 2's UNSAT falls through to it.

Consequence for the ordering gates: satisfiability no longer depends on the
ordering, and that is correct rather than a hole. A *saturation* claim from
the closure still requires a validated ordering, because a closure that ran
under an unvalidated one has proved nothing about completeness. The two tests
that pinned that now use unsatisfiable inputs, where there is no
ordering-independent route.

## Two optimisations that measured as wins and were reverted

Both are recorded because the measurements were convincing and both were wrong
or unsafe. This is the part of the work worth keeping.

### Restricted variable renaming — unsound

`ground_with_constants` instantiated every clause over every constant: `n^k`
instances, where instances that are variable renamings of each other look like
duplicates. Ordering a clause's variables by first occurrence and the domain by
symbol id, then requiring each value not to precede the previous, gives exactly
`C(n+k-1, k)` instances. For the two-constant, hundred-variable-per-clause half
of the division that is `2^100` → `101`; over the corpus it took 40 infeasible
groundings down to 28. It is also the kind of change that looks obviously
correct.

It is not. A variable permutation generally induces a **different** clause, so
"one representative per orbit of the renaming group" is not "one representative
per distinct instance".
`~group_element(Y) | product(X,e_4,Y) | ... | product(X,e_1,Y) |
~group_element(X)` over four constants (GRP123-4.004's `column_surjectivity`)
induces 16 distinct clauses; the restriction keeps 10 and drops six. The ground
set is then weaker than the problem, so a model of it need not satisfy the
problem.

`audit_casc_proofs` caught it, reporting `model violates axiom clause
column_surjectivity` on a problem whose reference answer is *also* Satisfiable —
a wrong model behind a right answer, which the reference check alone passes.
Only the kernel can see it.

The restriction is sound for the *refutation* direction, because a resolution
step using a renamed clause has a mirror using the representative. It is
unsound for satisfiability, which is all EPS is. `ground_with_constants` keeps
the exact `n^k` enumeration, and the estimate being exact is load-bearing: it
is what the instance cap refuses on.

`grounding_is_complete_over_distinct_induced_clauses` and
`instance_equality_is_clause_equality_not_renaming` pin the distinction, and
`satisfied_model_is_certified_by_the_kernel` closes the loop from outside —
`mrs-search` cannot depend on `mrs-proof-kernel`, so the check has to run where
both are visible. All three were verified to fail when the restriction is
reintroduced.

### Unique-name resolution of ground equality — safe reasoning, unsafe reachability

`expand_equality` refused any clause with a positive equality beside others,
because the closure cannot generate the congruence axioms such a literal needs.
Resolving them by the unique-name axiom instead — a ground disequality between
distinct constants is valid, a ground equality between them is false — needs no
congruence at all, is equisatisfiability-preserving in *both* directions, and
decides the whole NLP set plus `MSC008-1.010`. It took the measured EPS number
to 48/100 with every model kernel-certified.

It also turned a fail-closed `GaveUp` into a verdict that contradicts the
reference on `EPS/HWV042-1`: the reference is `Satisfiable`, and with the input
made reachable the SAT solver proved its ground set unsatisfiable. The
certifier did not get that far inside 120 s, so nothing wrong was emitted — but
the direction is wrong and would emit one given more time.

The problem's `reachableStateAxiom_201_1_1` clause is `VarState = constB200 |
... | ~reachableState(VarState)`: a disjunction over 201 equality literals,
whose ground instances are very sensitive to which constants the domain
collects. Whether the discrepancy is in the resolution or in MRS's lowering of
that problem was not established, and that is the deciding factor — a change
that moves a run off `GaveUp` onto a reference-violating verdict is
release-blocking whatever its cause. A `GaveUp` that agrees with the reference
is strictly better than a verdict that does not.

`non_unit_positive_equality_stays_outside_the_fragment` pins the strict
boundary, with the reasoning, so the next attempt starts from a pinned
boundary rather than from a measurement that looked like a win.

## A pre-existing soundness bug found on the way

`build_model_certificate` gave every constant its own domain element. For a
clause set containing a unit equation `a = b` — consumed by the union-find
pass, which rewrites every occurrence to one class representative — that emits
a certificate asserting `a != b`. The `Satisfiable` verdict was correct and the
model justifying it was not. This predates the 2026-09 work.

The class map is now threaded from `expand_equality` to the builder, and the
builder re-derives the requirement from the originals itself rather than
trusting its caller, since this failure mode is a silent wrong answer rather
than a crash. The fix is independent of the equality-boundary question: the
class map is a product of the union-find pass, which has always run.

## casc-sim and the harness

Four defects, all found by using casc-sim and none of them about EPS:

- **An undersized host turned the memory allowance into an OOM kill.** A
  casc-shaped mode asks for 128 GB; where the host has less, the OOM killer got
  there before the watchdog, so the harness recorded a kill — no SZS status at
  all — instead of a resource limit. The watchdog now enforces the effective
  ceiling. On a host that can represent 128 GB the two are equal, so a
  competition-shaped run is unaffected.
- **The dual search blocked on both tracks.** GRP123-4.004 is answered by the
  certifier in 113 ms and was reported as 109.498 s, because `invoke.sh` waited
  for the portfolio to use its full budget too. A disagreement needs two
  answers, so terminating the loser after the winner is definitive cannot hide
  one; `stopped=` in the `% SZS detail` line records when the comparison was
  not applicable. Same problem, 109.498 s → 0.54 s.
- **A proof route the kernel refused.** `sat_backed_refutation` could not cite a
  `cnf_transformation` parent, so the Tier-2 refutation route was kernel-rejected
  for any problem with a conjecture — `eq_unit_ground.p` went from
  `self_check=Certified` to `GaveUp` when Tier 2 started running first. Those
  rules are in the parent set now, each still verified by its own verifier; the
  FRAT trace is still bound to exactly the cited clauses.

## Making the certifier honour its own budget

Several problems produced **no status at all**, because the run was killed
rather than reporting a resource limit. That is the failure mode casc-sim
exists to surface. HWV053-1 spent 165 s on a 30 s budget and reached 81 GB; at
120 s it was killed at 240 s having printed nothing. Six unbounded steps, all
reachable from one problem:

1. `validate_ground_order` checked transitivity with a cubic triple loop over
   the atoms, no deadline — billions of whole-atom KBO/LPO comparisons on
   1400-odd atoms of arity 86. Replaced with rank agreement: sort by the
   comparison, then check every pair against the ranks. If the relation agrees
   with a total order it *is* that linear order and so is transitive, so this
   proves transitivity rather than approximating it.
2. The wave's budget counted inferences, and `MAX_CLAUSES` was checked only
   after a whole wave returned — a single wave could hold 40 000
   171-literal resolvents, ~600M terms once interned, before anything looked.
   The budget is now in *literals*, which is what the work scales with.
3. The merge that folds a finished wave into the index was 160 s of the 165 s
   and had neither a cap nor a deadline check.
4. `expand_equality` had no deadline check at all, and on a 1.9M-clause
   grounding it is one of the longest single steps.
5. `emit_sat_refutation` deduplicated its parent list with a linear
   `contains` inside a loop over every trace original — quadratic, and
   1.6 trillion comparisons on HWV039-1's 1.8M-entry manifest. The manifest
   cap only bounded the *payload*; it reached 15 GB before being killed.
6. `check_proof_trace` is linear in the event count and is now deadline-bounded
   through a new `check_proof_trace_until`, with a fail-closed
   `TraceError::Deadline`.

After these, `--time 30 / 60 / 120` on HWV053-1 takes 30.5 s / 60.6 s / 120.6 s
at 0.8–1.3 GB peak, and every run reports a status. NLP115-1 is not a
regression: at the 118 s budget the recorded 36.9 s solve is 69.3 s on the old
code and 51.3 s on the new, and at 60 s the old code overruns to 130 s and is
killed while the new one reports `GaveUp`. A 28-problem EPU sample shows no
coverage regression: 24 identical, 6 where killed runs became `GaveUp`, and 3
the other way.

**One case remains unbounded.** `EPU/HWV041-1` overruns because a *single* FRAT
RUP check over a very large antecedent set takes longer than the budget, so no
check interval inside the event loop helps. The fix belongs in the RUP scan
itself; that is the proof checker, so it is not being changed on the strength
of a benchmark observation. The failure mode is fail-closed meanwhile: the run
is killed, not answered wrongly.

## Result

`casc-30` EPS through the real harness, `crates/mrs-bench/casc.sh --divisions
eps --casc-times`, 120 s per problem, the CASC 8-worker dual split
(`workers=7+1`), 32-core Xeon / 128 GB. Banked as
`cert-eps-20260928`, against `cert-eps-20260926` for the same division:

| | 20260926 | 20260928 |
|---|---:|---:|
| `Satisfiable` | 12 | **42** |
| `GaveUp` | 21 | 13 |
| `Timeout` | 67 | 45 |
| `Error` | 0 | 0 |
| **reference violations (`ko`)** | 0 | **0** |
| invalid models | 0 | **0** |
| solved rows, mean wall | 46.14 s | **4.40 s** |
| solved rows, median wall | 36.86 s | **0.58 s** |
| gained / lost | — | **+30 / 0** |

**Nothing regressed.** All 12 problems the previous version solved still solve,
and the 30 gained are the GRP/E-Bench family (`GRP123-*` … `GRP132-*`), four
PUZ/SYN cases the closure used to spend its whole budget in, and five more SYN
problems.

The timing is the other half of the result and was not the goal. The median
solved row went from 36.9 s to 0.58 s because the SAT tier answers in
milliseconds where the closure spent tens of seconds failing to close — a
solved row no longer costs most of its budget to obtain. The `GaveUp` → 13 and
`Timeout` → 45 shift says the same thing from the failure side: the certifier
now spends its budget searching instead of refusing early.

Of the 42, **38 carry a model the proof kernel certifies** and **4 come back
`Inconclusive`, not `Rejected`**: the NLP family's models need more than
`MAX_MODEL_EVALUATION_WORK` (10⁸) evaluation steps, which is the documented,
pre-existing condition in `mrs-proof-kernel`'s own cap comment — the same four
problems the previous version solved, so this is not a regression, it is four
answers the checker cannot confirm.

### Independent reproduction, and what the 38 are actually made of

The certification above was re-run against a second, differently shaped harness
run: `casc-30-W8J1-eps-20260928`, `git_commit 00c329d`, **one job at a time** on
host `tlpnf9701` (32 logical / 16 physical cores, Xeon Silver 4108). This matters
because the "Measurement caveat" below records that the *first* pass at this
number was distorted by running two jobs on two physical cores, so a clean
single-job host is the right way to confirm it. It reproduces the split exactly:

| | `cert-eps-20260928` (`95f7984`, 8+1 workers) | `casc-30-W8J1-eps-20260928` (`00c329d`, jobs=1) |
|---|---:|---:|
| `Satisfiable` | 42 | 42 |
| invalid models | 0 | **0** |
| models certified | 38 | **38** |
| models uncertified | 4 | **4** |
| reference violations (`ko`) | 0 | **0** |

Two commits, two hosts, two worker configurations, one number. The 42 and the
38 are stable, and **`0` invalid models across 84 certified attempts** is the
part that matters: nothing wrong was ever emitted behind a correct-looking
answer.

The composition of the 38 is worth stating, because it is not 38 instances of
one capability. Of the 42 `Satisfiable` problems, **16 carry no axioms at all**
— after resolving `%include`, their statements are entirely
`negated_conjecture` clauses with no premises (the six `NLP*`, and
`SYN307-1`/`317-1`/`322-1`/`438-1`/`446-1`/`490-1`/`494-1`/`515-1`/`527-1`/`528-1`).
`SYN720-1` looks like a counterexample to this but is not: it is a bare
`include('Axioms/SYN001-0.ax')` and does have premises once the include is
followed. Counting axiom-free files by grepping the top-level file alone gets
this wrong in both directions, which is why the check resolves includes.

These 16 are **not** vacuous and must not be reported as such: 15 of them have
clauses with no negated literal, so the all-false interpretation does *not*
satisfy them and a model has to be genuinely found. They are ordinary
satisfiability problems, and 42/100 is a legitimate CASC score.

What they are is a materially easier problem than the other 26. With no
premises there is nothing to saturate: the ground set follows from the clauses
alone, so the answer comes out of the SAT tier in the milliseconds the timing
table above reports, whereas the 26 with axioms require establishing that a
quasi-group or a puzzle encoding is consistent. Both are real, and both count.
But a set cover that adds them as evidence of strategy capability is counting
two different skills in one column, and the composition belongs next to the
total whenever that number is interpreted.

This also explains *why* the uncertified four are the four: **all four
work-limit cases (`NLP115-1`, `NLP118-1`, `NLP120-1`, `NLP123-1`) are in the
empty-premise group.** So the certification gap sits entirely inside the easier
category, and none of the 26 premise-bearing models is uncertified. That is the
argument against spending effort here: raising `MAX_MODEL_EVALUATION_WORK` to
certify them would buy four empty-premise models at roughly 50 s of dense
evaluation each — which is precisely what the cap is right to refuse — while
leaving the 26 that represent the actual optimisation untouched. The cap should
stay where it is. Record the four as known-unverified instead.

Division-wide, 40 of the 100 EPS problems have no axioms (8 of the 100 EPU
problems do), so this is a property of the SAT track's problem mix rather than
of any one run. The EPU side is unaffected by all of this: its `Unsatisfiable`
rows are refutations, and refuting a clause set with no premises is a genuine
result, not a vacuous one.

### Provenance of that run

`run_meta.json` records `git_commit 95f7984e`, `git_branch main`, host
`teenf9901` — and `95f7984` *is* this work: it is the merge of this branch
(`ed60f00`) into `main`, and all six of this branch's commits are its ancestors.
So the harness run is the merged result, not a local approximation of it. Two
details worth keeping straight:

- `95f7984` is *later* than this branch's tip and also carries intervening
  mainline work (a 326-line delta in `certified.rs` and a new
  `clause.rs` change against `37d411c`). The run therefore measures the merge,
  not the branch tip in isolation. Nothing in this report depends on the
  difference — the division and its reference answers are the same — but the
  number belongs to the merge.
- `git_dirty: true` records some incidental local modification at run time.
  The archived streams still say which changes were exercised: every solved row
  carries `cert_tier=2` and `stopped=portfolio`, the tier-routing and
  `invoke.sh` early-stop markers.

Every `Satisfiable` answer is checked by the kernel's model validator through
`audit_casc_proofs` or `mrs-proover`, independently of the code that produced
it. **This is the gate that caught the renaming bug**, and it is the one that
matters for a satisfiability claim: a wrong model behind a right answer passes
the reference check.

### Measurement caveat, recorded because it changes the number

The first pass of this sweep reported 38, not 42. Four NLP problems
(`NLP115-1`, `NLP118-1`, `NLP120-1`, `NLP123-1`) came back `GaveUp` because the
sweep ran two jobs on two physical cores and their ~50 s of work did not fit in
120 s of contended wall clock. Re-run one at a time they solve in 49 s, 64 s
and 62 s. On a 2-core host the certified track is a single thread, so a
per-problem budget is best spent serially; casc-sim's worker warning does not
cover this, because the certified track never used the extra workers anyway.

`TIER2_MAX_ATOMS` was raised from 16 384 to 400 000 from measurement: with the
routing fixed, the atom count rather than the instance count became the binding
limit on which groundings reached the solver, and the atom set is not what costs
memory. `TIER2_MAX_GROUND_INSTANCES` is unchanged at 2 000 000, which is what
the exact estimate refuses on.

## Making the tier fit a small box (2026-09, `feat/eps-lowram-budget`)

The solved-row peak was **15.5 GB**, all of it the NLP family — the same four
problems whose models the kernel cannot confirm are the ones that materialize
1.9M ground instances. That is inside the 128 GB CASC allowance, but it is *more
than the development box has available* (13.9 GB), so those four rows were one
allocation away from an OOM kill that the harness records as a lost row. Four
findings, all measured on the 2-core / 15 GB box:

**A redundant copy of the whole ground set.** `certified_eq`'s contract is that
a predicate-only input passes through byte-identical, so for most of this
division `expand_equality` cloned every clause to reproduce it exactly. On
`NLP116-1` the grounding ends at 680 MB and the expansion pushed it to 1 557 MB:
~245 of the ~435 bytes per ground literal the tier peaks at, over half the peak,
to compute nothing. `expand_for_certification` now checks for an equality
literal first. `NLP116-1`: 2 093 → 1 069 MB.

**Refusal after the work was done.** The budget check sat inside the
materialization loop, so a run found out it was too big only once it had built
most of the set — and `Vec<Clause>` doubling held the old buffer alive while
building the new one. `EPS/HWV042-2` peaked at **20.8 GB on a 13.3 GB allowance**
to report `GaveUp` about a grounding it should never have started, and the
literal totals it needed (79.6M / 37.4M / 70.2M) were not even visible. The
grounder now makes one arithmetic pass with no allocation, refuses against the
exact totals, and reserves the exact capacity. Those three problems now peak at
3 085 / 2 061 / 3 085 MB.

**The ceiling was above what the OS would grant.** `effective_memory_mb` was
clipped to `MemTotal` (15 876 MB) against 13 897 MB actually available, so the
OOM killer beat the watchdog — the exact failure the earlier casc-sim fix was
meant to remove.

**And then a fix of that fix, which is the interesting one.** Clipping to
`MemAvailable` was the first answer and it is wrong under load: `MemAvailable`
moves, so a budget derived from it makes a run's limits depend on whatever else
is executing. The harness runs `--jobs N`, and each process would see a smaller
`MemAvailable` the more of them there were — a benchmark whose memory budget
shrinks as you parallelize it. Measured directly: the same problem got a 28.5M
literal budget in one process and 27.2M in another, minutes apart. The ceiling
is now the smaller of 85% of `MemTotal` and `MemTotal` less 1 GiB — a pure
function of the machine, so two processes agree and a batch reports the same
limits as a serial run. The 85% ceiling leaves margin below the measured
13 897 MB available on a 15 876 MB host; a 90% ceiling would still be above it.

Result: all 42 still solve, the four marginal rows now at 7.8–9.0 GB, and
`NLP118-1` verified to solve *under artificial load* at 8.9 GB. The banked
measurement used a 40.5M-literal cap (the `MemTotal - 1 GiB` calculation).
Review tightened that guard to 85% of total RAM, or 36.8M literals on this host;
the 42-row result above was not re-measured under that tighter cap. The four
large NLP groundings remain below it, while the 37.4M-literal `HWV048-2` is now
refused on this host and remains a competition-host measurement target.

| | peak on the NLP family | budget stability |
|---|---:|---|
| before | 15 488 MB (over the ceiling) | n/a |
| after the copy and refusal fixes | 7 835–8 980 MB | `MemAvailable`-derived, load-sensitive |
| after the stability fix | same | `MemTotal`-derived, stable |

`HWV048-2` (37.4M literals, 14.3 GB) is now inside the 60M-literal static
ceiling, so a 128 GB competition-shaped host can attempt it where before it
could not. `HWV042-2` (79.6M) and `HWV049-2` (70.2M) are outside it. Whether
`HWV048-2` then *solves* inside 120 s is unmeasured, and this box cannot
measure it — which is the note to leave for whoever has the memory.

A 20-problem EPU sample through the real dual-search path is unchanged: the 8
solves reproduce, and the 2 that miss (one a worker-count effect on 2 cores, one
a genuine hardware gap) behave identically on the pre-change binary, so they are
not regressions.

## What is left

The remainder is one problem, not two:

- **Groundings that cannot be materialized at all** — KRS/HWV-ar/SYO-ar (2
  constants, 100–280 variables per clause) and SYN816–SYN841 (26–48 constants,
  arity 40–56). A single atom containing every variable of a clause has one
  distinct instance per assignment, so no canonicalization helps, and the
  instances a solver needs are not the instances a grounder can enumerate.

  Taking this soundly needs lazy instantiation: search the Herbrand atoms with
  clause instances generated on demand from the falsified clause, then check the
  model against the *original* clause set rather than against a materialized
  instance set. That is a tier, not a patch, and it is the only remaining lever
  of size on this division.

## Reproducing

```bash
cargo build --release --bin mrs

# certified track alone, casc-sim at the CASC limit
MRS_HARDWARE=casc-sim MRS_SIM_TIME_FACTOR=1 MRS_WORKERS=2 \
    crates/mrs-bench/casc.sh --systems mrs --divisions eps --casc-times \
    --jobs 1 --output results/eps-casc-sim

# the refusal reason for one problem
TRACE_CERTIFY=1 ./target/release/mrs --time 120 --workers 1 \
    --schedule casc_eps --strategy 1 --certify-ordered EPS/<problem>.p 2>&1 \
    | grep CERTIFY

# the independent model check, which is the gate
cargo build --release -p mrs-bench --bin audit_casc_proofs
./target/release/audit_casc_proofs --run results/eps-casc-sim \
    --problems-dir crates/mrs-bench/problems/casc-30 --checks strict
```

On a host with fewer than 8 physical cores, casc-sim warns that the worker
count is not representative of a CASC entry and pins nothing. That does not
affect the certified track, which is a single thread either way — which is
precisely why measuring it here transfers.
