## Where EPU stood

The certified run `cert-epu-20260926` scored **9 of 100** (`9 Unsatisfiable`,

`SWV418`/`SWV419`/`SWV420`/`SWV421`/`SWV422` — FSM-reachability problems that

Classifying all 100 by EPR profile (`classify_epr_profile`) says where the

| profile | Unsatisfiable | GaveUp | Timeout | total |
|---|---|---|---|---|
| `epr_equality` | 1 | 21 | 17 | 39 |
| `pure_relational_epr` | 2 | 2 | 47 | 51 |

Both groups are blocked by the same thing, and it is not search power:

- **`epr_equality` is refused outright.** `instgen.rs` gates the whole loop on
  `is_pure_relational_epr` and returns `unsupported_epr_profile` for anything
  containing equality. 43 of the 100 problems never reach the one pre-pass
  designed for their shape (40 at a 3 s budget — the recorded route depends on
  how far the pre-pass gets before its own budget runs out, so the census is a
  range and has to be quoted with the budget it was taken at).
- **`pure_relational_epr` stalls.** Its instance generation takes the MGU of
  two model-satisfied complementary literals. The MGU binds one variable to
  another, so the resulting clause abstracts to the atom it came from, and the
  round adds nothing. On `MSC015-1.022` this is visible directly: 400 rounds
  executed, 399 instances generated, 423 clauses, and the same 24 clauses
  throughout. The run then falls through to a portfolio that has no way to do
  EPR reasoning.

The budget those two groups are given is also too small to be the fix. The
adaptive tier picks 750 ms for any problem whose estimated grounding exceeds
`10^5`; raising it to 25 s and 400 rounds by hand (`MRS_INSTGEN_TIMEOUT_MS`)
moved `PLA031-1.007` from 3 rounds to 5 and from 3 105 to 12 792 instances
without converging.

## Retracted: no ceiling adjustment — the division is scored out of 100

An earlier version of this report claimed the division's real ceiling was 82,
not 100: 18 files carry axioms and no `conjecture` role, so (the argument
went) no prover could score on them and the harness should subset to the
other 82. That argument is wrong, and the worked example it rested on is
wrong in both of its factual claims. It is retracted in full; the 18 files
stay in every denominator and the sweep harness covers the whole division.

The file list itself was accurate — these 18 have no `conjecture` role, and
`answers.tsv` grades all of them `Unsatisfiable`:

```
HWV057-1 HWV058-1 HWV060-1 HWV064-1 HWV065-1 HWV078-1 HWV081-1 HWV083-1
MSC024-1 PLA037-1 PLA039-1 PLA042-1 SYO588-1 SYO589-1 SYO591-1 SYO592-1
SYO594-1 SYO597-1
```

What does not follow is "no prover can score." An axiom-only CNF file with
status `Unsatisfiable` is a standard, scorable problem: refute the axioms.
"No conjecture" does not entail "must be Satisfiable" — it only means there
is no goal beyond the axioms themselves, and TPTP's authoritative status
asserts those axiom sets are jointly contradictory.

The report's concrete example, `HWV065-1`, was checked independently and came
back the other way. The report said the file has "no constants" and "the
expansion is satisfiable." In fact `true` and `false` occur as domain terms
(`p(true)`, `~p(false)`, and a `true != false` clause) — they *are* the
Herbrand universe, which is why the expansion is ~4× the clause count. And
the complete Herbrand expansion (60,922 ground clauses over `{true, false}`,
plus the `true != false` clause dropped as a true literal) is
**unsatisfiable**: MiniSat reports `UNSATISFIABLE` in 1.6 s, independently
confirmed by CaDiCaL. TPTP's `Unsatisfiable` is consistent with ground truth;
a prover scores on this file by refuting the axioms, as usual.

Overturning an authoritative status for 18 files would require exhibiting
satisfiability for each of them. The report exhibited none — not even the one
example, which refutes the claim. There is no ceiling adjustment, no
`epu-scoreable.txt` subset, and no `Satisfiable`-vs-`ko` dilemma: the harness
measures all 100.

## What was built

`crates/mrs-search/src/epr_ground.rs` searches the finite Herbrand expansion
directly, which is the mode this division actually wants. Instance generation
needs no special case for equality: `⊥ = c` is as much a ground instance as
`p(⊥)` is, so the `epr_equality` profile goes through the same loop. The SAT
abstraction, however, treats ground equality atoms as uninterpreted
propositions (canonically ordered, reflexive equalities simplified away, but
with no transitivity or congruence axioms) — equality reasoning proper lives
in the given-clause fallback, which runs superposition over the ground
instances. A refutation over ground instances is propositional in substance —
every clause in the derivation is an instance of an input clause — so it
lifts to first order clause by clause with no abstraction step, which is what
makes the proof route sound.

- all-`⊥` bootstrap (one genuine instance per clause, so the set stays a
  relaxation of the input), then a **widening ladder**: one variable over the
  pivots → one over the whole domain → two over the pivots → all variables
  uniform → all variables over the pivot cross product, with the
  model-driven falsification rule running inside each rung. Variables past a
  rung's depth are completed with `⊥`, so every candidate is a genuine ground
  instance the solver can use (an earlier cut emitted partial instances the
  abstraction dropped on arrival, and its rungs searched nothing on
  wide clauses — see below)
- optional **equality splitting** (`MRS_EPR_SPLIT=1`, off by default), which
  prunes each rung's candidate list by the clause's own split support. Correct,
  soundness-tested, and measured to be worth nothing here; see *Equality
  splitting* for the numbers and the reason
- two proof routes, because a bounded propositional BFS blows up well before
  the SAT solver does: the BFS first, then the given-clause loop over the
  ground instances *alone* with AVATAR
- grounding and proof get separate budget shares, sized from the sum of the
  schedule's strategy budgets — the right scale because every schedule
  partitions the CLI wall clock into per-strategy slices, and the pre-pass
  runs sequentially in every worker mode — and RSS is watched, because the
  first cut turned a 15 s run into 395 s at 13 GB. Known limitation: worker
  budgets are not reduced by pre-pass elapsed, so an opt-in run's total wall
  is the pre-pass share *plus* the full portfolio (sizing from the minimum
  slice was tried and reverted: a 2% diagnostic share clamps the pre-pass to
  the 500 ms floor, which the proof reserve then eats whole)

## The result that mattered most was a failure

An intermediate version reported **13 of 15 refuted** on a stratified subset —
apparently 0 → 13, a 3× improvement. Every one of those proofs failed strict
verification:

```
% SZS status VerifiedBad : node c231: instantiate conclusion is not a parent instance
```

The `⊥` bootstrap replaced *every* term, not just variables, so
`m_cell_v_token(c_e_h_3,X0)` became `m_cell_v_token($bot,$bot)`. That is not an

SAT abstraction was being driven unsatisfiable for a reason unrelated to the
problem. `bot_instance_replaces_variables_not_constants` pins it down.

13 of 15 `Unsatisfiable` with 13 of 15 `VerifiedBad` is precisely what the
certification gate exists to catch, and it is why `cert-epu-20260926` records a
`proofs/` tree and an `audit.csv` rather than a pass/fail on the SZS line alone.
**An EPU number quoted without its proof column is not a number.**

The profile classification and the distinction between grounding and ordinary
superposition remain valid. Note what the claim is: the

search power. The instantiation restriction

## Retracted: nullary predicates are not Herbrand elements

`collect_constants` builds the Herbrand universe of an EPR clause set: the set
of constants to instantiate variables over. A review incorrectly claimed it
also needed to include nullary predicate symbols. That claim confused two AST
variants:

```rust
Atom::Pred(symbol, args) // a predicate atom; args=[] means a proposition
Term::App(symbol, args)  // a term; args=[] means a constant
```

These symbol namespaces have the same `SymbolId` representation, but distinct
logical roles. The nullary predicate `esk1_0` is a propositional atom, not a
domain element. Only nullary function terms (`Term::App(_, [])`) belong in the
Herbrand universe. Adding predicate symbols as constants conflates atoms with
terms and can inflate the grounding domain dramatically. The implementation
and its regression test have been corrected to exclude them.

The previous census and resulting measurements are invalidated:

| | count |
|---|---|
| CASC-30 EPU problems containing at least one nullary predicate | 100 of 100 (irrelevant to the term domain) |
| claimed affected count / retracted domain sizes | **not valid evidence** |

`is_epr` is right: nullary predicates are EPR atoms. They do not affect the
Herbrand domain or variable instantiation.

| | before | after |
|---|---|---|
| `HWV065-1` domain / estimated expansion | 2 / 60 923 | 6 / 548 283 claim retracted |
| `HWV065-1` pre-pass verdict | `grounding_exhausted` (SAT) | post-change observation invalidated |
| `model_fixpoint` across the division | 63 | 56 claim retracted |

The independently established status of `HWV065-1` remains useful, but the
claimed larger domain, altered SAT verdict and the revised `model_fixpoint`
census came from an invalid domain construction. They must not be used to infer
anything about the pre-pass or its search space.

**Method note.** The instance set the pre-pass holds is a *relaxation* of the
problem — every clause in it is an instance of an input clause — so a `Sat`
verdict says the relaxation is satisfiable, not that the problem is. That gap is
what hid this for as long as it did. Two diagnostics close it and are worth
keeping: `TRACE_EPR_DUMP=<path>` writes the asserted instance set as TPTP, and
`MRS_EPR_PROBE=1` re-decides it with the ground given-clause loop whatever the
SAT verdict. Dumping `HWV065-1`'s set and counting the distinct symbols in it is
what made "domain 2" look wrong against 5 600 real symbols in the file.

## Equality splitting: implemented; the earlier measurement was negative

The negative A/B below predates the instance-ladder corrections in this review.
It records what the earlier build did, but does not establish whether splitting
helps the corrected ladder; that requires a fresh measurement.

`split_support` implements the rule in the sense of López-Gil, Ordinary and
Anzai, for the EPR case. A clause whose equality literals all pin one variable
to constants

```text
c₁ = X ∨ c₂ = X ∨ … ∨ cₙ = X ∨ R(X)
```

only ever forces `R` at values in `D \ {c₁…cₙ}`; grounding it at the `cᵢ`
spends the budget asserting something the clause already says. So each rung's
candidate list is pruned by the clause's split support. It is
soundness-tested by exhaustive witness search — every emitted candidate is
verified to be a substitution instance of the input clause — and it is gated
behind `MRS_EPR_SPLIT=1` because the measurement is negative.

**In the earlier build, it did not pay.** The following numbers were measured
on the full division before the ladder corrections and are not a verdict on the
current implementation:

| | value |
|---|---|
| EPU problems containing at least one clause of the split shape | **20 of 100** |
| those 20, concentrated in | `HWV104-1` (1 107 split clauses), `HWV103-1` (65), `HWV107-1` (36), `HWV089-1` (33) |

The 80 problems with no split-shaped clause get nothing from the rule at all. And
in the 20 that do, the rungs are *budget*-capped rather than search-capped, so
pruning candidates does not buy coverage — it buys more of a smaller set, and
the cap is reached at a different point:

| problem | `epr_generated`, split off | split on |
|---|---|---|
| `HWV104-1` | 177 445 | 176 609 |
| `HWV087-1` | 264 561 | **369 829** |
| `HWV039-1` | 64 536 | 64 536 |

and across the whole division the total instance count moves from 10 381 690 to
10 359 366, a 0.2% reduction, with the fallback mix unchanged
(56 `model_fixpoint`, 37 `grounding_timeout`, 1 `sat_solver_unknown`).

The specific hope that did not survive contact is worth recording, because the
shape looks perfect for it: the HWV family has split clauses with ~200
disjuncts over a ~205-constant domain, which should have pruned a state variable
from 205 values to about 5 and made the remaining variables' cross product
affordable. It does not, because **those clauses have no `R(X)`** — they are
`⋁ᵢ cᵢ = X` and nothing else, so they assert that `X` is one of the `cᵢ` and
constrain nothing further. There is no rest for the split to restrict, and
`split_support` correctly declines to treat them as split variables. A rule that
pruned them anyway would be asserting a false restriction, and would look like a
large speedup right up until it produced a wrong answer.

So the rule stays in the tree, sound and tested, off by default, with the
measurement attached. What the division actually needs is not a sharper
instantiation rule but the defect buckets — the still-open `sat_solver_unknown`
and `MSC024-1` proof-extraction cases — plus a first-order technique on the
~90 problems whose expansions are astronomically large no matter how the
instances are chosen (`est` exceeds 10⁸ for 24 of 100 and saturates `u64` for
more). For those, superposition in the portfolio, not grounding, is the
mechanism that has to get better.

| arm | Unsatisfiable | VerifiedGood | reference violations | total wall | peak RSS |

| pre-pass off (default) | **8** | 8/8 | 0 | 10 719 s | 14 991 MB |

The eight are the same eight in both arms, and seven of the eight are the

things about it need saying rather than glossing.

**The missing ninth is `SYN837-1`, and it is the host, not the change.** It is
EPR (`pure_relational_epr`) and the pre-pass engages on it in *both* arms — the
telemetry is present in each, 13 fields apiece — and both arms time out on it.
Run in isolation at `--time 120 --workers 2` it returns `GaveUp` in 133 s, not
`Unsatisfiable`. The reference run solved it with 8 workers on a 16-core host.
This host has 2 physical cores, so `--workers 2` is the honest setting and it is
not enough for that problem. The A/B cannot separate the two, and does not need
to: the arms agree on it.

**One row shows `Error`, and it is an OOM kill.** `HWV127-1` — 652 680 clauses
after clausification, 9 545 MB peak — produced no SZS status line at all in the
off arm and was recorded `Error` at 112 s. Run alone it finishes in 39 s with
`GaveUp`, 8.2 GB peak, exit 0, which is also the reference run's status for it.
Two such problems at once on 15.8 GB is what the `casc` mode warns about before
it happens:

```
% Hardware: hardware=casc workers=8 host_physical_cores=2 mem_budget_mb=131072
  effective_mem_mb=13494 mem_unrepresentable=1
```

A 128 GB allowance on a 15.9 GB host is not a limit, and `mem_unrepresentable=1`
says so. The fix is the job count, not the code: at `EPU_JOBS=2` the pair of
concurrent problems is the problem. **Any number from a run with
`mem_unrepresentable=1` carries this caveat**, which is why the harness records
the hardware line per problem.

Every number in this subsection is superseded. The pre-pass coverage conclusion
must be remeasured with the corrected term-only universe before drawing a
conclusion about its default.

## Measurement on this host

The CASC-30 EPU division is 100 problems at a 120 s wall clock on 8 physical
cores and 128 GB. The host used here is an i3-5010U with **2 physical cores, 4
logical CPUs and 16 GB**. A faithful run is not available: the division is
about 13 CPU-hours of 8-core work against roughly 1.3 CPU-hours here, and
`casc-sim` cannot simulate what it does not have — it says so on every run:

```
% Hardware warning: hardware=casc-sim wants 8 workers but this host offers
  only 2 usable physical core(s), so the worker count is not representative
  of a CASC entry
% Hardware warning: hardware=casc-sim sets a 131072 MB allowance but this host
  has only 15876 MB, so a run needing more is killed by the host before that
  allowance applies
% Hardware warning: casc-sim could not pin to 8 physical cores (cannot simulate
  8 physical cores: only 2 available); the run is not CPU-constrained
```

So the numbers above are **relative** — A/B on the same host, same subset, same
worker count pinned to real physical cores — and none of them is a CASC
coverage figure. `crates/mrs-bench/epr_ab_sweep.sh` is the harness, and it
records the worker count and time limit in its output so a number cannot be
quoted without the conditions it was measured under.

Wall-clock adherence *was* verifiable here, and it is why the budget split and
the RSS guard exist: the pre-pass's first cut respected neither, and
`PLA031-1.007` ran 395 s and reached 13 GB on a 15 s limit before the guard
existed.

## The full-division measurement needed to decide default-on

The default decision requires the whole division, at the competition shape,
with the proof column attached. The archived arms below were not matched (see
the caveat above), so they do not settle that decision:

```bash
# A: pre-pass off (current default behaviour)
EPU_JOBS=2 ./crates/mrs-bench/epr_ab_sweep.sh epu-A-baseline

# B: pre-pass on
EPU_JOBS=2 MRS_EPR_GROUND=1 ./crates/mrs-bench/epr_ab_sweep.sh epu-B-prepass
```

`EPU_JOBS` is how many problems run at once, and it is bounded by the host:
`casc.sh --jobs N` launches N *separate* `mrs` processes that do not coordinate,
and under `casc` each takes 8 workers with no CPU pinning (pinning is
`casc-sim`-only, `src/main.rs`), so N jobs is 8N threads. **A 16-physical-core
host therefore sustains `EPU_JOBS=2` and no more** — it cannot do the arms at
`--jobs 1` any faster than that, and asking for more silently produces numbers
that still say `workers=8` while being wrong. The script detects physical cores
and refuses to oversubscribe, printing the job count the host does support;
`EPU_ALLOW_OVERSUB=1` overrides it and records `shape_valid=0` in
`conditions.txt` so an overridden run cannot be read as a CASC number later.

At `EPU_JOBS=2` each arm is ~1 h 40 m. The residual risk is that unpinned
threads are not perfectly isolated, so a problem at the 120 s wall clock can
lose a `Unsatisfiable` to a `GaveUp` it would otherwise have won; repeat the
matched arms and retain the arm-A cross-check rather than relying on a raw
difference between arms.

`epr_ab_sweep.sh` now runs `casc.sh` underneath with `--casc-times` and
`--hardware casc`, so the division's official 120 s and the CASC 8-worker /
128 GB shape are the defaults, and it runs `audit_casc_proofs --checks strict`
and prints the `VerifiedGood` column next to the solved count. It writes, per
arm:

| file | what |
|---|---|
| `run/run.csv` | the harness's own record, with commit, division, time limit and `use_casc_times` |
| `conditions.txt` | the pre-pass flag, hardware mode, jobs and time arguments, plus `git_commit`, `git_dirty`, `binary_sha256`, host and `rustc`; `casc.sh` records the resolved worker binary hash in `run_meta.json`, and `systems/mrs/invoke.sh` verifies it before execution |
| `certification/audit.csv` | per-problem `strict_status` |
| `certification/audit-summary.txt` | the certification summary |
| `epr_telemetry.csv` | `epr_generated` / `epr_rounds` / `epr_falsifying` per problem, joined from the archived stderr |

That last file answers a different question from "did the pre-pass win":
`epr_generated` of 0 means the ladder never ran, which is a defect rather than
a result. Check both arms' recorded binary hashes before interpreting outcomes.

`--subset` keeps the stratified 18 for a quick look. It is a diagnostic, not a
measurement — a subset's solved count is not a division number.

### What decides the default

| A (off) | B (on) | Verdict |
|---|---|---|
| n/100, all VerifiedGood | more than n, **all VerifiedGood** | flip the default |
| n/100 | more than n, some not VerifiedGood | keep off; the coverage is not checkable |
| n/100 | n/100, same problems, same statuses | keep off; neutral, and a default change with no coverage is what the discipline exists to prevent |
| n/100 | fewer than n, or any `ko` | stop: B is a regression |

A `ko` — a status disagreeing with the answer key — is release-blocking in
either arm and outranks everything else in the table.

### What the host needs

A bare RHEL box is enough; there is no Nix dependency for building or running
(the Nix flake is for the development shell and CI, and every script here calls
`cargo`/`mrs` directly).

```bash
# toolchain: edition 2024 / resolver 3 needs rustc >= 1.85; the repo is on 1.98.1
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y
source "$HOME/.cargo/env"
rustc --version          # expect 1.98.1

# CaDiCaL is vendored and compiled by the `cc` crate as C++17. No cmake, no
# make, no system SAT solver. gcc 7+ is enough; the build probes for
# `closefrom` and defines NCLOSEFROM when absent, so glibc 2.28 (RHEL 8) and
# 2.34+ (RHEL 9) both work.
sudo dnf install -y gcc-c++    # or: sudo dnf install -y clang

# harness prerequisites, all in base RHEL
sudo dnf install -y bc          # casc.sh arithmetic
# bash >= 4, awk, sed, grep, date, xargs, timeout: present
# python3: optional, only for the epr_telemetry.csv join; its absence is
#          non-fatal and the script says the file is missing rather than
#          reporting a number as if telemetry existed.
```

Shape check before spending 7 hours — the number means nothing without it:

```bash
# want 8 physical cores and 128 GB
lscpu -p=core | grep -v '^#' | sort -u | wc -l
grep MemTotal /proc/meminfo
```

Build, once:

```bash
git fetch origin && git checkout epu-instgen-equality && git pull --ff-only
cargo build --release --bin mrs -p mrs-bench --bin audit_casc_proofs
```
