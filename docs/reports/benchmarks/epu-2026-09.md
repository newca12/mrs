# EPU: profiling the division, and a sound grounding pre-pass that does not yet pay

> Status: current. Branch `epu-instgen-equality`, commit `a92186f`. Measured on
> `crates/mrs-bench/problems/casc-30/EPU` on an i3-5010U (2 physical cores,
> 16 GB) — see *Measurement on this host* for what that does and does not
> license. Every refutation reported here is checked by
> `mrs-proover --strict`, and the check is the reason one section below reads
> as a failure.

## Where EPU stood

The certified run `cert-epu-20260926` scored **9 of 100** (`9 Unsatisfiable`,
`27 GaveUp`, `64 Timeout`, `9/9` proofs `VerifiedGood`). The 9 are all
`SWV418`/`SWV419`/`SWV420`/`SWV421`/`SWV422` — FSM-reachability problems that
happen to have a short propositional refutation once their `trans` closure is
expanded.

Classifying all 100 by EPR profile (`classify_epr_profile`) says where the
other 91 go:

| profile | Unsatisfiable | GaveUp | Timeout | total |
|---|---|---|---|---|
| `epr_equality` | 1 | 21 | 17 | 39 |
| `pure_relational_epr` | 2 | 2 | 47 | 51 |
| (clausification exceeds the probe budget) | 6 | 4 | 0 | 10 |

Both groups are blocked by the same thing, and it is not search power:

- **`epr_equality` is refused outright.** `instgen.rs` gates the whole loop on
  `is_pure_relational_epr` and returns `unsupported_epr_profile` for anything
  containing equality. 39 of 100 problems never reach the one pre-pass
  designed for their shape.
- **`pure_relational_epr` stalls.** Its instance generation takes the MGU of
  two model-satisfied complementary literals. The MGU binds one variable to
  another, so the resulting clause abstracts to the atom it came from, and the
  round adds nothing. On `MSC015-1.022` this is visible directly: 400 rounds
  executed, 399 instances generated, 423 clauses, and the same 24 clauses
  throughout. The run then falls through to a portfolio that has no way to do
  EPR reasoning.

The budget those two groups are given is also too small to be the fix. The
adaptive tier picks 750 ms for any problem whose estimated grounding exceeds
`10^5`; raising it to 25 s and 400 rounds by hand (`MRS_INSTGEN_TIMEOUT_MS`)
moved `PLA031-1.007` from 3 rounds to 5 and from 3 105 to 12 792 instances
without converging.

## The division's real ceiling is 82, not 100

**18 of the 100 problem files in `problems/casc-30/EPU` contain axioms and no
`conjecture` role at all**, while `systems/reference/answers.tsv` grades every
EPU problem `Unsatisfiable`:

```
HWV057-1 HWV058-1 HWV060-1 HWV064-1 HWV065-1 HWV078-1 HWV081-1 HWV083-1
MSC024-1 PLA037-1 PLA039-1 PLA042-1 SYO588-1 SYO589-1 SYO591-1 SYO592-1
SYO594-1 SYO597-1
```

Two consequences. First, no prover can score on those 18, so 9/100 is really
9 of a possible 82 and 9/82 is the number to beat — reporting against 100
hides a fifth of the division being unreachable. Second, answering them
correctly would mean `Satisfiable`, which the reference grades as `ko`; the
harness's `division_polarity` treats any non-`Unsatisfiable` answer on EPU as
a polarity violation. Nothing here changes the corpus, but the sweep harness
subsets to the 82 so that a measurement is not diluted by them.

`HWV065-1` makes the shape concrete: 15 233 `cnf(...,axiom,...)` clauses, no
goal, 5 000 binary `esk*(X,Y)` predicates, no constants. Its Herbrand expansion
is 60 923 ground clauses and the expansion is satisfiable, which is the right
answer for a goal-less problem and is graded as a failure.

## What was built

`crates/mrs-search/src/epr_ground.rs` searches the finite Herbrand expansion
directly, which is the mode this division actually wants. Equality needs no
special case: `⊥ = c` is as much a ground instance as `p(⊥)` is, so the
`epr_equality` profile goes through the same loop. A refutation over ground
instances is propositional in substance — every clause in the derivation is an
instance of an input clause — so it lifts to first order clause by clause with
no abstraction step, which is what makes the proof route sound.

- all-`⊥` bootstrap (one genuine instance per clause, so the set stays a
  relaxation of the input), then a **widening ladder**: one variable over the
  pivots → one over the whole domain → two over the pivots → all variables
  uniform → all variables over the pivot cross product, with the
  model-driven falsification rule running inside each rung
- two proof routes, because a bounded propositional BFS blows up well before
  the SAT solver does: the BFS first, then the given-clause loop over the
  ground instances *alone* with AVATAR
- grounding and proof get separate budget shares, and RSS is watched, because
  the first cut turned a 15 s run into 395 s at 13 GB

## The result that mattered most was a failure

An intermediate version reported **13 of 15 refuted** on a stratified subset —
apparently 0 → 13, a 3× improvement. Every one of those proofs failed strict
verification:

```
% SZS status VerifiedBad : node c231: instantiate conclusion is not a parent instance
```

The `⊥` bootstrap replaced *every* term, not just variables, so
`m_cell_v_token(c_e_h_3,X0)` became `m_cell_v_token($bot,$bot)`. That is not an
instance of anything — the instance is `m_cell_v_token(c_e_h_3,$bot)` — so the
SAT abstraction was being driven unsatisfiable for a reason unrelated to the
problem. `bot_instance_replaces_variables_not_constants` pins it down.

13 of 15 `Unsatisfiable` with 13 of 15 `VerifiedBad` is precisely what the
certification gate exists to catch, and it is why `cert-epu-20260926` records a
`proofs/` tree and an `audit.csv` rather than a pass/fail on the SZS line alone.
**An EPU number quoted without its proof column is not a number.**

## Where it stands

With the soundness fix, on a 28-problem spread of the scoreable division
(every third problem, so the EPR profiles and both outcome classes are
represented), the pre-pass refuted **nothing** with an acceptable proof and
changed no outcome in either direction:

| arm | Unsatisfiable | GaveUp | Timeout | total wall clock |
|---|---|---|---|---|
| pre-pass off (default) | 3 | 8 | 17 | 201.3 s |
| pre-pass on | 3 | 8 | 17 | 203.1 s |

All 28 statuses are identical, and the cost is +1.8 s in total — the ladder
reaches `model_fixpoint` in well under a second on 22 of the 25 problems where
there is anything EPR to ground, and the run is wall-clock-capped either way.
Peak RSS stays under 0.7 GB, and the earlier cut that reached 13 GB is what the
RSS guard and the phase split exist to prevent.

So it is cheap and neutral rather than harmful, and it stays **off by default**
(`MRS_EPR_GROUND=1` enables it): "measured neutral" is not "earned a place in the
default path", and shipping a default-path change with no measured coverage is
the thing this repo's discipline exists to prevent.

The diagnosis stands and the route is not wrong — the pre-pass is the only
thing in the tree that searches `epr_equality` at all, and the ground set it
builds is sound. What is missing is search power. The instantiation restriction
is the issue: these problems are four-variable typed encodings
(`node18(I0,I1,X,Y) | ~node19(I0,I1,X,Y) | node17(I0,I1,X)` over a 56-constant
domain), so binding two of four variables covers 1/16 of the combinations a
refutation needs and the abstraction never closes.

**The next piece is equality splitting**, in the sense of López-Gil, Ordinary
and Anzai: decompose on a disjunction of equalities so the domain partitions
and the abstraction stops needing every variable bound at once. That is the
technique E and Vampire use on exactly this problem family, and it is a
substantive addition rather than a tuning change. A cheaper interim step is
E-matching — generate instances from the constants the goal and the units
already mention, which is a strictly larger version of the pivot set the
pre-pass has now.

## Measurement on this host

The CASC-30 EPU division is 100 problems at a 120 s wall clock on 8 physical
cores and 128 GB. The host used here is an i3-5010U with **2 physical cores, 4
logical CPUs and 16 GB**. A faithful run is not available: the division is
about 13 CPU-hours of 8-core work against roughly 1.3 CPU-hours here, and
`casc-sim` cannot simulate what it does not have — it says so on every run:

```
% Hardware warning: hardware=casc-sim wants 8 workers but this host offers
  only 2 usable physical core(s), so the worker count is not representative
  of a CASC entry
% Hardware warning: hardware=casc-sim sets a 131072 MB allowance but this host
  has only 15876 MB, so a run needing more is killed by the host before that
  allowance applies
% Hardware warning: casc-sim could not pin to 8 physical cores (cannot simulate
  8 physical cores: only 2 available); the run is not CPU-constrained
```

So the numbers above are **relative** — A/B on the same host, same subset, same
worker count pinned to real physical cores — and none of them is a CASC
coverage figure. `crates/mrs-bench/epr_ab_sweep.sh` is the harness, and it
records the worker count and time limit in its output so a number cannot be
quoted without the conditions it was measured under.

Wall-clock adherence *was* verifiable here, and it is why the budget split and
the RSS guard exist: the pre-pass's first cut respected neither, and
`PLA031-1.007` ran 395 s and reached 13 GB on a 15 s limit before the guard
existed.

## Reproducing

```bash
cargo build --release

# relative A/B on a stratified, scoreable subset
EPU_TIME=15 EPU_WORKERS=2 \
  ./crates/mrs-bench/epr_ab_sweep.sh baseline
EPU_TIME=15 EPU_WORKERS=2 MRS_EPR_GROUND=1 \
  ./crates/mrs-bench/epr_ab_sweep.sh epr-ground

# the harness, and then the gate that decides whether a number counts
MRS_HARDWARE=casc-sim ./crates/mrs-bench/casc.sh \
  --edition casc-30 --systems mrs --divisions epu --time 15 --jobs 1 \
  --subset /tmp/epu-scoreable.txt --output results/epu-run
cargo run --release -p mrs-bench --bin audit_casc_proofs -- \
  --run results/epu-run/run.csv --problems-dir crates/mrs-bench/problems/casc-30 \
  --output results/epu-run/certification --checks strict
```

Never quote an EPU number without the `VerifiedGood` column beside it.
