## 1. The score

| | count | of 400 |
|---|---:|---:|
| **Solved (`Unsatisfiable`, verdict `ok`)** | **107** | **26.8 %** |
| `Timeout` | 271 | |
| `GaveUp` | 22 | |
| `Theorem` / `Satisfiable` / `Error` | 0 | |
| Reference or polarity violations | 0 | |

Every one of the 107 refutations is **kernel-certified**: the strict audit
replays each proof through `mrs-proof-kernel` and returns `VerifiedGood` 107
times out of 107 applicable, with 0 `VerifiedBad`, 0 `Unknown`, 0 `Timeout`,
0 `Error`. The other 293 rows are `N/A: Incomplete` — the audit's name for a
row that produced no proof to check. There is no unsoundness signal anywhere in
this run, and no partial credit is being claimed: the division score is 107,
full stop.

Two provenance notes, both of which change how the number may be quoted:

- **The run is not CASC-shaped.** `hardware=adaptive` on 16 physical cores
  with a 47 GB budget is neither the canonical 8 cores / 128 GB nor
  `casc-sim`'s enforced imitation of it. Per AGENTS.md §11 this is a
  development measurement. Do not put 26.8 % next to a published CASC score.
- **`run_meta.json` and the run disagree about the limit.** `run_meta.txt`
  records `time_limit=120`, `default_time_limit: 120`, while `run.log` reports
  `[casc] Time limits: ueq=180s` and all 400 rows carry `timeout=180`. The
  `--casc-times` override supplied the official 180 s and won; the metadata
  field records the flag default and was never updated. Anyone reading
  `run_meta.json` alone will date this run wrongly.

## 2. The finding that matters: 257 → 107

`codex.db` holds a CASC-J13 run over the same 400 UEQ problems at the same
180 s with the same 8 workers, on a host of the same family (Silver 4108). It is
reported as **257/400 (64.3 %)** in
[`codex/status-2026-09-11.md`](../codex/status-2026-09-11.md) §3 and in
[`summary-2026-09.md`](summary-2026-09.md). Row-by-row against this run:

| | count |
|---|---:|
| Solved by both | 96 |
| Solved by `codex.db`, **not** by this run | **161** |
| Solved by this run, **not** by `codex.db` | 11 |

Only 37 % of the previously solved set is still solved. This is not a host
band. The FNE report's ±4-problem host band was established by measuring
`processed_per_s` on the same problems; here the same measurement moves in the
opposite direction and by two orders of magnitude:

| measurement, on the 146 regressed rows that have telemetry on both sides | `codex.db` | this run |
|---|---:|---:|
| `processed_per_s`, median | **1649.5** | **116.0** |

**A 14× throughput loss on exactly the problems that were lost.** On the 96
commonly-solved rows, where both configurations do succeed, median wall time
went 1.92 s → 7.76 s and this run is the slower of the two on 61 of 96. The
regression is in the engine, not in the schedule's luck, and not in which
problems happen to be hard.

Two commits between the `codex.db` run and `c07cac9` are the prime suspects,
and both are visible in the archived telemetry.

### Suspect 1: cross-strategy sharing was turned off by default

`ce7bdc5` (2026-09-23) changed `SearchConfig::default().shared_pool_poll_interval`
from `500` to `0`, and `3e962a8` made the opt-in explicit in the harness and
docs. The `codex.db` rows show sharing live on essentially the whole division:
`shared_published > 0` on 385 of 400 rows, `shared_imported > 0` on 347, and
**on all 257 rows it solved**. This run has `shared_published=0
shared_imported=0` on all 377 rows that emitted telemetry — sharing is
completely off, as documented.

UEQ is the division where this should matter most: the pool's entire payload
is *positive unit equalities*, which is precisely the clause shape a
unit-equality division produces. The per-row numbers are consistent with
sharing having been load-bearing. `LAT018-1`:

```
codex.db  elapsed_ms=2841   processed=5819    imported=20303   result=Refutation
this run  elapsed_ms=62357  processed=25647   imported=0       result=Refutation
```

The old run reached the refutation in 2.8 s having *imported* 20 303 shared
equalities; the new run spent 62 s and 4.4× the processed clauses to find the
same proof with nothing to import. `GRP002-10` is the same shape: 0.76 s with
4 836 imports against 42.7 s and none.

### Suspect 2: the UEQ portfolio was reordered on unvalidated evidence

`b214a13` (2026-09-25) changed `CASC_UEQ_ORDER` from
`[11, 4, 2, 8, 14, 1, 15, 3, …]` to `[4, 8, 12, 11, 2, 14, 15, 1, …]`. The
archived `strategy_ids` confirm the swap: the old rows read
`0:11;1:4;2:2;3:8;4:14;5:1;6:15;7:3` and this run reads
`0:4;1:8;2:12;3:11;4:2;5:14;6:15;7:1`. The justification was the solo greedy
set-cover in
[`greedy_portfolios_20260925.md`](../../results/greedy_portfolios_20260925.md),
which that document explicitly flags as unvalidated for the 8-worker
cooperative case: *"Validate the 8-worker schedules with cooperative portfolio
sweeps before treating solo set-cover coverage as cooperative performance."*
That validation does not appear to have been run before the order shipped.

Note the direction of the evidence. The old order leads with s11, s4, s2, s8;
the new one drops s2 and s3 out of the first eight and promotes s12. On the
`codex.db` evidence the old eight are the better set. A 150-problem move
attributable to a portfolio reorder alone would be implausible; a 150-problem
move with sharing switched off is not.

### What would settle it

One controlled A/B, same host, same session, `--workers 8`, the four cells
being the old and new orders × sharing off and `MRS_SHARED_POOL_INTERVAL=500`.
`--portfolio` makes this a four-command experiment with no rebuild:

```bash
# needs: nix develop -c cargo build --release, and
#        crates/mrs-bench/problems/casc-j13 + systems/reference/answers_casc-j13.tsv
for order in 11,4,2,8,14,1,15,3  4,8,12,11,2,14,15,1; do
  for pool in 0 500; do
    MRS_WORKERS=8 MRS_SHARED_POOL_INTERVAL=$pool \
      ./crates/mrs-bench/cooperative_portfolio_sweep.sh \
      casc-j13 ueq "$order" 180 1 \
      "results/ueq-ab-${order//,/_}-${pool}"
  done
done
```

All four cells must run on one host in one session against a baseline from that
same host; the FNE report's ±4-problem host band is the reason. Read the
`shared_published` / `shared_imported` columns of each `run.csv` before
comparing counts, to confirm the pool was actually live in the `500` cells and
actually dead in the `0` cells — this run's own telemetry makes that check
cheap, and skipping it is how a sharing A/B silently measures nothing.

Until that runs, the honest statement is that UEQ coverage fell by 150 problems
across a window containing one change that removed a division-specific
optimisation and one that swapped a portfolio on evidence its own source
document calls unvalidated. Attributing it to either alone would be a guess.

## 3. The 22 `GaveUp` rows are mislabelled timeouts

All 22 ran the full budget and none saturated. Their `timeout=` counts are
`4` (×10), `5` (×1), `6` (×2), `7` (×9) — never 8, against `timeout=8` on 248
of the 271 `Timeout` rows. The mechanism is in
`raw_search_result` (`crates/mrs-search/src/lib.rs:410-434`), which scans for
`Refutation`, then `Saturated`, then `ResourceOut`, then `GaveUp`, and only
falls through to `Timeout` if none matched. So a run in which some strategies
hit the deadline and others returned through a fail-closed give-up path is
reported as `GaveUp` regardless of which dominated.

Nothing is unsound — `GaveUp` is a legitimate fail-closed answer and the
precedence order is deliberate. But the label makes a claim the telemetry
contradicts: it says the prover *chose* to give up on a problem it was still
searching. These 22 should be read as timeouts for scoring purposes, and
`GaveUp` counts are not comparable across runs that differ in this precedence
sensitivity. The same artefact is visible in `codex.db`, where 128 of 400 rows
are `GaveUp` with `timeout=7` or `8` and `saturated=0`.

Distinguishing the two needs per-strategy `return_reason` in the aggregate
`% SZS detail` line. `instgen.rs` and the certified paths already set
`fallback_reason` / `return_reason` per strategy; the portfolio rollup drops
them.

## 4. 23 rows have no telemetry at all

23 problems ran to `wall_time_s=180.000` with an **empty** `failure_detail`,
empty `processed_per_s`, empty `peak_memory_mb`, and a stdout containing
nothing whatsoever: `ARI764-1`, `GRP508-1`, `GRP654-10/11/12`, `GRP655-10/13`,
`GRP660-10`, `GRP661-1`, `GRP662-1`, `GRP664-10`, `GRP667-10`, `GRP690-1`,
`GRP695-1`, `GRP705-1`, `GRP765-1`, `GRP024-5`, `LAT139-1`, `LAT142-1`,
`KLE110-10`, `NUN135-1.028`, `BOO073-1`, `ARI764-2`.

`invoke.sh` deliberately gives the prover a 178 s soft deadline
(`SOFT_TIME = TIME_LIMIT - 2`) so that its own time-check fires and prints an
SZS status before an external kill can take the process out mid-search with no
output. On these 23 the 2 s margin was not enough: teardown ran past it and
the harness's `timeout $((tlimit + 10))` killed the process with nothing
flushed. `casc.sh` classifies that correctly as `Timeout`, so **the score is
unaffected** — but 5.8 % of the division is undiagnosable, and 13 of the 23 are
GRP, the family most affected by §2. The same rows are no-telemetry in the
`codex.db` run for 5 of them, so this is long-standing rather than new.

## 6. What the budget is and is not buying

| | median | max |
|---|---:|---:|
| wall time, solved rows | 8.8 s | 180.2 s |
| peak memory, solved rows | 3 085 MB | 29 711 MB |
| peak memory, `Timeout` rows | 15 374 MB | 63 880 MB |

Only 4 of the 107 solved rows took longer than 150 s and only 8 took longer
than 120 s. The median solve is under 9 s against a 180 s budget, so **the
division is not budget-limited** — the wins are cheap and the losses are
qualitatively out of reach rather than narrowly missed. `ALG240-1` at
`wall_time_s=180.152` is the one row that solved *past* the stated limit, by
0.15 s; it has a complete 41-node proof and is correctly scored, but it would
not have survived a hard 180 s kill, so a CASC-shaped run should be expected to
lose it.

`saturated=0` on all 377 rows that reported telemetry: no strategy ever hit a
saturation ceiling, so the portfolio is not being throttled by its own
completeness guards. `generated/processed` is 32 on solved rows against 52 on
timeouts, and the timeouts are not short of throughput — they emit 236 million
clauses across 271 problems and close none of them.

## 7. What I would do next, in order

1. **Run the four-cell A/B in §2.** It is four commands, no rebuild, and it is
   the difference between "UEQ regressed 150 problems" and "UEQ regressed 150
   problems because we removed the equality pool from the one division built
   out of unit equalities." Nothing else in this report should be acted on
   before that number is known.
2. **If sharing is confirmed as the cause, re-enable it for `casc_ueq` only.**
   The opt-out at `ce7bdc5` was a global default change made for
   reproducibility, and reproducibility is a real concern — but a global default
   is the wrong instrument when the payload is division-specific. A per-schedule
   interval in `named.rs`, with the no-sharing control retained in the test at
   `named.rs:870`, gets both.
3. **Fix the 2 s teardown margin in `invoke.sh`.** 23 rows of undiagnosable
   output is a harness defect, not a prover result, and it will keep corrupting
   future runs in whichever family happens to be slowest to tear down.
4. **Roll per-strategy `return_reason` into the aggregate detail line** so §3
   stops being unanswerable from `run.csv`.
5. **Only then re-fit `casc_ueq`.** Fitting a portfolio on top of an engine
   that has lost a division-specific optimisation measures the wrong thing.
6. **Do not report 107/400 as a CASC result**, and do not report 26.8 % as a
   regression rate either: the comparable pair for that is 257 → 107 on the
   same 400 problems, and its cause is not yet established.

  --run <run-dir>/run.csv \

**What is and is not banked.** `docs/results/` holds `run.csv`, the audit
summary, `run_meta.json`, and a derived `.tsv` — 216 KB in total, following the
`eps-casc-sim-20260928-*` precedent of banking the CSV and the summaries. The
6 MB of raw stdout/stderr under `raw/mrs/ueq/` is **not** banked, so the
re-audit step above needs the original run directory, and that directory
(`/home/fr22192/pve/crates/mrs-bench/results/campaign-ueq-W8C16J1-20260930`) is
not a git repository. If the raw streams are wanted as durable evidence they
should be committed or archived deliberately, not left in place. The `run.csv`
carries a `raw_stdout_sha256` per row, so any copy that is made can be checked
against the banked run.
