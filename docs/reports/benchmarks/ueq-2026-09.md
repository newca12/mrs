Two provenance notes, both of which change how the number may be quoted:

- **The run is not CASC-shaped.** `hardware=adaptive` on 16 physical cores
  with a 47 GB budget is neither the canonical 8 cores / 128 GB nor
  `casc-sim`'s enforced imitation of it. Per AGENTS.md §11 this is a
  development measurement. Do not put 26.8 % next to a published CASC score.
- **`run_meta.json` and the run disagree about the limit.** `run_meta.txt`
  records `time_limit=120`, `default_time_limit: 120`, while `run.log` reports
  `[casc] Time limits: ueq=180s` and all 400 rows carry `timeout=180`. The
  `--casc-times` override supplied the official 180 s and won; the metadata
  field records the flag default and was never updated. Anyone reading
  `run_meta.json` alone will date this run wrongly.

### Historical telemetry note 1: cross-strategy sharing differed

`ce7bdc5` (2026-09-23) changed `SearchConfig::default().shared_pool_poll_interval`
from `500` to `0`, and `3e962a8` made the opt-in explicit in the harness and
docs. The legacy `codex.db` telemetry shows `shared_published > 0` on 385 of
400 rows and `shared_imported > 0` on 347. This run has
`shared_published=0 shared_imported=0` on all 377 rows that emitted telemetry.
This establishes a configuration/telemetry difference only; it does not show
that sharing accounts for 150 valid solves.

UEQ produces positive unit equalities, so sharing remains a reasonable topic for
a new controlled experiment. The historical per-row telemetry is not a valid
coverage comparison. For example, `LAT018-1`:

### Historical telemetry note 2: the UEQ portfolio order differed

`b214a13` (2026-09-25) changed `CASC_UEQ_ORDER` from
`[11, 4, 2, 8, 14, 1, 15, 3, …]` to `[4, 8, 12, 11, 2, 14, 15, 1, …]`. The
archived `strategy_ids` confirm the swap: the old rows read
`0:11;1:4;2:2;3:8;4:14;5:1;6:15;7:3` and this run reads
`0:4;1:8;2:12;3:11;4:2;5:14;6:15;7:1`. The justification was the solo greedy
set-cover in
[`greedy_portfolios_20260925.md`](../../results/greedy_portfolios_20260925.md),
which that document explicitly flags as unvalidated for the 8-worker
cooperative case: *"Validate the 8-worker schedules with cooperative portfolio
sweeps before treating solo set-cover coverage as cooperative performance."*
That validation does not appear to have been run before the order shipped.

The strategy IDs confirm different orders, but the unsound legacy status labels
cannot establish that the old order was better or quantify any effect of the
reorder. The solo set-cover evidence was also not a cooperative measurement.

Any renewed schedule/sharing study must compare current builds on the same host
and problem set, strictly audit every emitted proof, and use multiple
replicates. The old 257/400 database count is not a valid baseline for that
experiment.

## 3. The 22 `GaveUp` rows are mislabelled timeouts

All 22 ran the full budget and none saturated. Their `timeout=` counts are
`4` (×10), `5` (×1), `6` (×2), `7` (×9) — never 8, against `timeout=8` on 248
of the 271 `Timeout` rows. The mechanism is in
`raw_search_result` (`crates/mrs-search/src/lib.rs:410-434`), which scans for
`Refutation`, then `Saturated`, then `ResourceOut`, then `GaveUp`, and only
falls through to `Timeout` if none matched. So a run in which some strategies
hit the deadline and others returned through a fail-closed give-up path is
reported as `GaveUp` regardless of which dominated.

Nothing is unsound — `GaveUp` is a legitimate fail-closed answer and the
precedence order is deliberate. But the label makes a claim the telemetry
contradicts: it says the prover *chose* to give up on a problem it was still
searching. These 22 should be read as timeouts for scoring purposes, and
`GaveUp` counts are not comparable across runs that differ in this precedence
sensitivity. The same artefact is visible in `codex.db`, where 128 of 400 rows
are `GaveUp` with `timeout=7` or `8` and `saturated=0`.

Distinguishing the two needs per-strategy `return_reason` in the aggregate
`% SZS detail` line. `instgen.rs` and the certified paths already set
`fallback_reason` / `return_reason` per strategy; the portfolio rollup drops
them.

## 4. 23 rows have no telemetry at all

23 problems ran to `wall_time_s=180.000` with an **empty** `failure_detail`,
empty `processed_per_s`, empty `peak_memory_mb`, and a stdout containing
nothing whatsoever: `ARI764-1`, `GRP508-1`, `GRP654-10/11/12`, `GRP655-10/13`,
`GRP660-10`, `GRP661-1`, `GRP662-1`, `GRP664-10`, `GRP667-10`, `GRP690-1`,
`GRP695-1`, `GRP705-1`, `GRP765-1`, `GRP024-5`, `LAT139-1`, `LAT142-1`,
`KLE110-10`, `NUN135-1.028`, `BOO073-1`, `ARI764-2`.

`invoke.sh` deliberately gives the prover a 178 s soft deadline
(`SOFT_TIME = TIME_LIMIT - 2`) so that its own time-check fires and prints an
SZS status before an external kill can take the process out mid-search with no
output. On these 23 the 2 s margin was not enough: teardown ran past it and
the harness's `timeout $((tlimit + 10))` killed the process with nothing
flushed. `casc.sh` classifies that correctly as `Timeout`, so **the score is
unaffected** — but 5.8 % of the division is undiagnosable, and 13 of the 23 are
GRP, the family most affected by §2. The same rows are no-telemetry in the
`codex.db` run for 5 of them, so this is long-standing rather than new.

## 6. What the budget is and is not buying

| | median | max |
|---|---:|---:|
| wall time, solved rows | 8.8 s | 180.2 s |
| peak memory, solved rows | 3 085 MB | 29 711 MB |
| peak memory, `Timeout` rows | 15 374 MB | 63 880 MB |

Only 4 of the 107 solved rows took longer than 150 s and only 8 took longer
than 120 s. The median solve is under 9 s against a 180 s budget, so **the
division is not budget-limited** — the wins are cheap and the losses are
qualitatively out of reach rather than narrowly missed. `ALG240-1` at
`wall_time_s=180.152` is the one row that solved *past* the stated limit, by
0.15 s; it has a complete 41-node proof and is correctly scored, but it would
not have survived a hard 180 s kill, so a CASC-shaped run should be expected to
lose it.

`saturated=0` on all 377 rows that reported telemetry: no strategy ever hit a
saturation ceiling, so the portfolio is not being throttled by its own
completeness guards. `generated/processed` is 32 on solved rows against 52 on
timeouts, and the timeouts are not short of throughput — they emit 236 million
clauses across 271 problems and close none of them.

## 7. What to do next

1. Treat 107/400 as the strictly verified outcome of this archived campaign,
   not as a CASC score: this run used `hardware=adaptive` on a 16-core host.
2. Do not describe the 257-to-107 raw-label difference as a regression. The
   257 legacy count is unsound/unverified, so it cannot serve as a baseline for
   measuring sharing, portfolio order, or current coverage.
3. If revisiting sharing or schedule choices, run matched experiments with the
   current sound producer, strict audits, and identical hardware/problem sets.
   Start with two paired blocks and add pairs if outcomes disagree or the effect
   is marginal; two pairs are a screen, not a significance claim.
4. The current-run telemetry findings in §§3–6 (give-up rollup, missing output,
   and resource behavior) remain observations about this campaign's artifacts;
   they do not depend on accepting the legacy 257 count.

**What is and is not banked.** `docs/results/` holds `run.csv`, the audit
summary, `run_meta.json`, and a derived `.tsv` — 216 KB in total, following the
`eps-casc-sim-20260928-*` precedent of banking the CSV and the summaries. The
6 MB of raw stdout/stderr under `raw/mrs/ueq/` is **not** banked, so the
re-audit step above needs the original run directory, and that directory
(`/home/fr22192/pve/crates/mrs-bench/results/campaign-ueq-W8C16J1-20260930`) is
not a git repository. If the raw streams are wanted as durable evidence they
should be committed or archived deliberately, not left in place. The `run.csv`
carries a `raw_stdout_sha256` per row, so any copy that is made can be checked
against the banked run.
