# MRS 2027 Implementation Plan

This is the executable roadmap for making MRS both competitive and
self-verifying. It replaces the earlier calendar-based plan with a
dependency-ordered plan driven by the current proof audits.

The plan has two goals that must remain separate:

1. **CASC performance:** maximize the number of problems solved by the
   eight-core parallel MRS portfolio.
2. **Proof trust:** emit a theorem or unsatisfiable result only when an
   independent strict checker has certified the refutation in the selected
   release mode.

Search performance and proof certification are developed together, but their
metrics are never conflated. A raw MRS refutation is not automatically a
certified proof. Agreement with a TPTP reference answer is not a mathematical
soundness certificate.

## How To Use This Document

Every implementation task must identify its phase, affected files, tests,
benchmark command, telemetry, and exit gate. Do not skip a phase because a
later phase appears more attractive.

The authoritative documents are:

| Document | Authority |
|---|---|
| `docs/PLAN_2027.md` | Implementation order, responsibilities, and gates |
| `docs/VERIFIER_SPEC.md` | Normative strict-kernel trust boundary |
| `docs/BENCHMARKS.md` | Append-only empirical benchmark and audit record |
| `docs/RELEASE_CHECKLIST.md` | Release validation and repository gate |
| `docs/TODO_CASC.md` | Short-term CASC experiments after the gates here |

The local CASC-30 EPU, EPS, and ICU suites are legacy CASC-30 regression

with the actual CASC-J13 entry scope. The current target divisions for the
FOF/UEQ entry are FNE, FEQ, and UEQ. The official CASC-2027 divisions and MRS
registration must be confirmed separately before competition freeze.

## 2. Scope And Trust Model

### 2.1 Product boundaries

`mrs` is the high-performance search engine. It may use the existing parallel
portfolio, AVATAR, CWA, FVO, AC indexing, clause sharing, SInE, InstGen, and
experimental guidance.

`mrs-proover` is the broad ProoVer checker. Its external ATP, MRS fallback,
finite-model, and dialect adapters may remain useful for competition scoring,
but they are not part of the strict-kernel trust argument.

`mrs-proof-kernel` is the independent strict checker. It must not depend on
`mrs-search`, external ATP binaries, process adapters, or the result of an MRS
search.

### 2.2 Explicit modes

| Mode | Purpose | Positive theorem output |
|---|---|---|
| Search | Fast development and raw portfolio measurement | Generated result may be reported diagnostically |
| Audit | Search plus archived proof/model audit | Raw and verified counts reported separately |
| Certified | Trusted release path | Only strict-certified refutations |
| Competition verifier | ProoVer scoring and broad TSTP coverage | Competition policy only |

The existing `--self-check` is a synchronous development gate. It is not yet
the final CASC coordinator because it checks only after the portfolio has
already selected a candidate and stopped sibling searches.

### 2.3 Non-negotiable invariants

1. No theorem or unsatisfiable status is emitted in certified mode without a
   strict `Certified` result.
2. `Rejected`, `Inconclusive`, timeout, parse failure, missing provenance, and
   verifier infrastructure failure are never positive proof evidence.
3. The strict kernel recomputes accepted conclusions from actual parents.
4. Inference names and status annotations are metadata, not proof evidence.
5. Every proof parent exists and is reachable from the final `$false` root.
6. Proof output is topologically ordered by dependencies, not by clause ID.
7. Fresh Skolem and definition symbols are unique within one problem.
8. AVATAR and CWA are certified only with complete explicit case-split data.
9. Filtered, incomplete, or heuristic search cannot produce a positive model
   result.
10. Reference-answer agreement is always reported separately from soundness.
11. All performance experiments use eight physical cores as the CASC baseline.

## 3. Architecture Target

The target pipeline is:

```text
TPTP input
   |
   v
clausification with explicit provenance
   |
   v
parallel MRS search
   |
   v
candidate refutation DAG
   |
   v
post-refutation proof elaborator
   |
   v
deterministic TSTP proof bundle
   |
   v
independent strict kernel
   |
   +-- Certified -> release theorem/unsatisfiable result
   +-- Rejected -> discard candidate and continue search
   +-- Inconclusive/Timeout -> discard candidate and continue search
```

The migration has two stages.

### 3.1 Stage A: post-refutation elaboration

Keep the hot search loop mostly unchanged. When a candidate wins, extract its
minimal proof graph and expand composite transformations into exact replayable
steps.

This is the first implementation target because it can improve proof coverage
without copying large witness structures through every inference. It must fail
closed when the compact search provenance does not determine a unique valid
derivation.

### 3.2 Stage B: typed proof-producing search

Introduce immutable proof-node IDs and typed inference witnesses. Search clauses
refer to proof nodes, while the proof arena retains derivations after search
indexes delete or simplify operational clauses.

Typed witnesses are required where post-hoc elaboration cannot safely recover:

- selected resolution literals and substitutions;
- factoring and equality-inference choices;
- superposition positions and orientations;
- demodulation rewrite sequences;
- AC normalization;
- definition and shared-clause mappings;
- AVATAR/CWA branch certificates.

## 6. Phase 1: Confirmed Soundness Defects

### Objective

Remove actual invalid proof generation before expanding strict-kernel coverage.

### Primary target

The six CASC-30 FEQ ladder `VerifiedBad` rows. Then repeat for the four
CASC-J13 FEQ ladder `VerifiedBad` rows.

### Procedure for each failure class

1. Reproduce the proof from the archived raw output.
2. Run strict, MRS-only, and ladder checks independently.
3. Inspect the exact first failing proof step.
4. Determine whether the problem is symbol naming, definition provenance,
   leaf identity, Skolemization, demodulation, superposition, AC handling,
   shared-clause remapping, or another transformation.
5. Add a minimal regression fixture and an adversarial mutation.
6. Fix proof generation or provenance.
7. Re-run the fixture, the affected division, and the full relevant audit.

Do not change the strict kernel merely to make an invalid generated proof pass.

### Symbol and definition requirements

- Sanitize TPTP symbol names before rendering, but also make the sanitized
  names collision-safe.
- Allocate fresh symbols from a problem-global namespace.
- Do not use independently generated `goal_d0`-style names across workers.
- Record exact definition identities and transitive dependencies.
- Validate emitted `introduced(definition, ...)` syntax against the parser,
  strict kernel, competition verifier, and external TSTP checker.

### ICU containment

Add a generic resource policy, not a single hard-coded ICU clause threshold:

- per-strategy clause and term ceilings;
- memory watchdog telemetry;
- graceful `ResourceOut` or `GaveUp` status;
- complete worker cleanup;
- no conversion of resource exhaustion into satisfiability.

### Exit gate

- Zero ladder `VerifiedBad` in the audited FEQ fixtures.
- Every fix has a regression test.
- No new strict or ladder bad result in EPU, FNE, or UEQ.
- ICU resource failures terminate cleanly and are classified.

## 7. Phase 2: Post-Refutation Proof Elaborator

### Objective

Improve strict proof coverage by expanding the existing compact proof graph only
after search finds a candidate.

### New module

```text
crates/mrs-proof/src/elaborate.rs
```

Suggested interface:

```rust
pub fn elaborate(
    proof: &[Clause],
    symbols: &SymbolTable,
) -> Result<ElaboratedProof, ElaborationError>;
```

The exact API may differ, but the elaborator must be pure and deterministic.

### Elaboration rules

#### Demodulation

For a composite demodulation node:

1. Validate the target parent and all rewrite parents.
2. Reconstruct each candidate rewrite using the indexed clause contents.
3. Record literal position, term position, oriented rule, and substitution.
4. Apply exactly one rewrite per intermediate node.
5. Continue only when the intermediate clause equals the next expected clause.
6. Stop with `Inconclusive` if the trace is ambiguous, cyclic, exceeds a
   bounded search limit, or cannot reproduce the final conclusion.

Do not choose an arbitrary rewrite sequence merely because it reaches the same
final clause.

#### Definitions

- Add explicit fresh-symbol declarations only when the definition is already
  structurally justified.
- Preserve all definition dependencies.
- Never turn an unsupported formula into a definition by annotation alone.

#### Ordering

- Insert intermediate nodes into the proof graph.
- Topologically sort by actual parent edges.
- Do not rely on numeric clause IDs.

### Measurements

Compare before and after elaboration:

- strict `VerifiedGood`;
- strict `VerifiedBad`;
- strict `Unknown`;
- ladder `VerifiedGood`;
- ladder `Timeout`;
- proof node count;
- serialized proof bytes;
- elaboration time;
- failed elaboration count and reason.

The plan must not promise that elaboration eliminates all unknowns or timeouts.
It is successful only if it improves replay coverage without accepting a bad
proof.

### Tests

- One-step demodulation.
- Multi-step demodulation.
- Rewrite-position mutation.
- Rewrite-order mutation.
- Cyclic rewrite rules.
- Ambiguous rewrite failure.
- Nested definition dependency.
- Stable topological export.
- Existing golden strict-certified proofs.

### Exit gate

- Existing strict-certified golden proofs remain certified.
- No adversarial mutation is certified.
- Elaboration is deterministic.
- Missing replay information returns `Inconclusive`.
- At least one measured audit category improves without a new `VerifiedBad`.

## 9. Phase 4: Typed Proof Arena and Witnesses

### Objective

Replace lossy parent-plus-rule provenance where post-hoc elaboration cannot
recover exact choices safely.

### Affected areas

- `crates/mrs-core/src/clause.rs`;
- `crates/mrs-core/src/term_bank.rs`;
- `crates/mrs-search/src/state.rs`;
- `crates/mrs-calculus/src/`;
- `crates/mrs-proof/src/extract.rs`;
- `crates/mrs-proof/src/tstp.rs`;
- `crates/mrs-proof-kernel/src/lib.rs`.

### Proof identity

Introduce stable proof-node IDs separate from operational `ClauseId`s. The
proof arena is append-only and retains nodes after search deletes clauses from
processed or passive indexes.

An operational clause must reference its proof node. `ClauseSource` may remain
as a compatibility projection during migration, but new inference code must
create typed witnesses.

### Required witness data

| Rule | Witness data |
|---|---|
| Resolution | Parent IDs, selected literal indices, standardization mapping, substitution |
| Factoring | Parent ID, retained/removed literal indices, substitution |
| Equality resolution | Equality literal index and substitution |
| Equality factoring | Equality indices, side choices, substitution, ordering check |
| Subsumption resolution | Target/subsumer mapping and exact deleted literal |
| Condensation | Literal mapping and unifying substitution |
| Superposition | Equality side, target literal, term path, orientation, substitution |
| Demodulation | Ordered rewrite steps, rule IDs, positions, substitutions |
| AC normalization | AC symbols, canonicalization witness, source axioms |
| CNF | Source formula, definitions, extraction path, dependency closure |
| Skolemization | Existential, active universals, witness symbol, exact matrix relation |
| AVATAR/CWA | Split parent, branch index/polarity, context, branch root, roll-up |
| Shared lemma | Canonical proof package and receiver mapping |

### Exit gate

- Proof extraction survives LRS pruning, backward simplification, clause
  deletion, shared imports, and AVATAR dormancy.
- Mutating any witness causes strict rejection or inconclusive status.
- TSTP output is dependency-topological and deterministic.

## 11. Phase 6: Asynchronous Candidate Certification

### Objective

Prevent an uncertified first refutation from stopping the whole portfolio.

### Coordinator behavior

```text
search worker finds candidate
    -> candidate queue
    -> elaboration
    -> strict certification
       -> Certified: cancel siblings and emit result
       -> Rejected: discard and continue
       -> Inconclusive/Timeout: discard and continue
```

The coordinator must retain enough search time for certification. Test both:

- eight search workers plus a dedicated certification thread;
- seven search workers plus one certification worker.

Use the canonical eight physical cores as the comparison baseline and record
oversubscription explicitly if any experiment uses it.

### Telemetry

- candidate count;
- candidate rejection count;
- candidate reasons;
- elaboration time;
- strict-kernel time;
- proof bytes and nodes;
- time remaining at candidate discovery;
- certified candidate index;
- raw versus certified solve result.

### Exit gate

- A rejected first candidate cannot suppress a later certified candidate.
- Certified mode never emits theorem after strict rejection, timeout, or
  inconclusive verification.
- End-to-end certified score and search-only score are both reported.

## 12. Phase 7: Search Performance Optimization

Performance work may run experimentally before Phase 6, but no optimization is
promoted to the certified release without proof and audit gates.

### 12.1 Measurement hardening

Add or preserve a benchmark `run_id` containing:

- commit and binary hashes;
- edition, division, problem;
- command and environment;
- host and CPU configuration;
- outer jobs and internal workers;
- timeout and TPTP root;
- raw output paths and hashes;
- search result and certification result.

Parse `% SZS detail` into typed telemetry. Distinguish external timeout,
internal timeout, LRS-pruned incomplete search, SInE-subset incompleteness,
InstGen fallback, parse failure, panic/OOM, resource termination, and complete
saturation.

### 12.2 SInE

SInE already exists. Do not add a second implementation or enable it globally
without controls.

Compare:

- unpruned;
- conservative;
- standard;
- aggressive;
- SInE with at least one full-axiom worker.

Record retained axioms, symbol depth, goal connectivity, first useful inference,
passive size, result completeness, and proof coverage. A filtered subset that
saturates is `GaveUp` unless completeness is independently established.

### 12.3 EPR and InstGen

Instrument the existing path in `crates/mrs-search/src/instgen.rs`:

- invocation and route;
- rounds;
- generated instances;
- SAT variables and clauses;
- elapsed time;
- fallback reason;
- proof extraction result.

Separate EPR, EPR-with-equality, ground, and non-EPR profiles. Preserve
refutation proof extraction. Variable-bearing model results remain fail closed
until Phase 8.

### 12.4 UEQ guidance

Test conservative combinator and non-AC guidance for COL, LCL, RNG, and SWX.
Keep the current UEQ portfolio as a mandatory raw and certified regression
baseline. Any goal transformation must have explicit namespace and proof
provenance.

### 12.5 Clause sharing and LRS

For shared clauses:

- compare sharing disabled, equality-only, predicate-unit, and ground-lemma
  controls;
- record eligible, published, imported, duplicate, rejected, and used counts;
- preserve complete ancestor chains and variable standardization.

For LRS:

- record target size and queue size before/after pruning;
- record discarded goal-distance bands;
- compare wall-clock, fixed-iteration, disabled, and protected-goal controls;
- never turn incomplete search into a model result.

### 12.6 ICU containment

Add per-strategy memory telemetry, clause/term ceilings, watchdogs, graceful
resource statuses, and complete worker cleanup. Do not use one hard-coded clause
count as the only safety policy.

### Exit gate

Every performance phase must provide:

1. fixed-corpus A/B results;
2. per-division and per-morphology deltas;
3. overlap-aware failure accounting;
4. strict and competition proof audits;
5. raw telemetry and reproducible commands;
6. no new ladder `VerifiedBad` result;
7. no new strict-certified adversarial mutation.

## 13. Phase 8: EPS Model Certificates

EPS produced 17 `Satisfiable` model results, but proof auditing correctly marks
them `N/A: Model`. They are not independently certified.

A model certificate must include and validate:

- finite domain and non-emptiness;
- every constant interpretation;
- every function interpretation, if present;
- every predicate interpretation;
- equality semantics;
- all original formulas and resolved includes;
- correct conjecture polarity;
- complete ground clause coverage;
- a deterministic model digest.

Until this exists, EPS results may be reported as generated and
reference-compatible only. Do not call them certified models.

EPU refutation certification and EPS model certification are separate projects.
Do not use success in one as evidence for the other.

## 16. Definition Of Done

MRS is self-verifying when all of the following hold:

- every certified refutation has a deterministic, self-contained proof DAG;
- every reachable proof step is independently replayed by
  `mrs-proof-kernel`;
- post-hoc elaboration never guesses missing derivations;
- typed witnesses cover every transformation not safely recoverable after
  search;
- an uncertified first candidate cannot suppress a later certified candidate;
- shared clauses preserve proof identity and definition dependencies;
- AVATAR and CWA certificates contain complete branch data;
- model results are not described as refutation certificates;
- benchmark reports distinguish generated, reference-compatible, ladder, and
  strict-certified outcomes;
- no adversarial mutation is strict-certified;
- current CASC canaries and EPU regression gates pass;
- the certified CASC path meets the measured performance target;
- all release checks pass from a clean checkout.

The final competition claim must be phrased narrowly:

> In certified mode, every emitted refutation result passed the independent
> strict kernel under the documented proof, resource, and dialect limits.

It must not be phrased as:

> Every raw MRS result, reference-compatible benchmark row, or satisfiability
> result is mathematically certified.
